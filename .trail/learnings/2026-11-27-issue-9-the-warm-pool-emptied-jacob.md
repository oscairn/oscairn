decided: FANTOM d1's slow TSO Carol Bells (1.6-1.9 s, open load 1.2 s, the VA 'Init Normal' loaded new instead of taken from the keep-warm pool) came from three places that let the pool go at a switch although nothing sounded. (1) Session::estimate's Steps loop broke at once when every outgoing node was idle ('nothing left to ring out: a cut') before it tried the silent ones, so with nothing sounding and the two Performances past the ceiling (every plain TSO reload; any switch while a take records, whose rings are committed) it was a cut: 'opened at once ... would not fit' logged and openPerformance's letGo(all) emptied the pool. Now the break needs a sounding node given up first (i>0): nothing sounding releases silent nodes largest first as memory needs and is seamless. (2) openPerformance after a cut or a memory release let every warm instance go; with memory classes it now lets go only the excess over the room evictOpportunistic computes, through letGoResidents. (3) The two pre-read trims (memory classes' room, and the 'available' floor against MemAvailable) charged the incoming's whole estimate although it takes over warm instances and the outgoing's free instances of its plugins, which already sit in committed memory / outside MemAvailable: counted twice, so the trims ran on a thin, drifting margin (MemAvailable 356-385 MiB against a 200 MiB floor plus WIMP's estimate), which is why some engine lifetimes trimmed and others did not; in the slow lifetime the arpeggiator that usually absorbed the trim was already gone, so the VA went. Now both charge 'fresh' = estimate less those takeable bytes (capped per plugin at what it needs). letGoResidents orders largest first, longest idle among equals (was idle x bytes), as the owner asked (same rule as issue 330's silent nodes); evictOpportunistic keeps its LRU order (RFC 0021, control-performance-switch-workers checks it). The trim lines now log freed MiB, room or need, and the incoming's new MiB, so the device shows each decision. ruled out: the recorder keeping deleted takes' rings (Recorder::service frees a finished take's rings and recounts; a take still recording does count, legitimately). Also: a test where the incoming takes over nothing still loses the warm instance before the read, correctly: the outgoing stays resident during read(), so the peak is both. watch out: without memory classes a cut or memory release still lets every warm instance go (nothing measures room there). The VA's own second (the cost of every cold VA part) is unverified on the device: its core builds band-limited tables once per process (va core/laws.cpp buildTables, about 35 ms on an M-series Mac; the triangle loop calls pow and rolloffDb inside the per-sample loop although they depend only on the harmonic), so each fresh VA worker pays that, likely several hundred ms on the A53; a plugin fix (VA repo). control-performance-switch-steps*'s 'steps, kept warm' fails before the fix in all three variants. control-performance-switch-workers' 'G -> C, room for C but not the instrument kept warm' had built its room on the double count (C's whole estimate though its four Samplers come from the pool); it now gives room for C's new memory (estimate less the Samplers' resident bytes) and checks that is more than the instrument holds.
